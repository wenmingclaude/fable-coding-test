## 2. 朴素验证器

[`verify/naive.cpp`](../verify/naive.cpp)（约 75 行）：每个版本一个 `std::string`，每个操作用
`substr` / 拼接 / 逐字符循环按题面定义直译，例如

```cpp
// MOVE
std::string cut  = t.substr(l, r - l);
std::string rest = t.substr(0, l) + t.substr(r);
version.push_back(rest.substr(0, p) + cut + rest.substr(p));
```

它与 `src/` 不共享任何代码（包括输入解析），时间和内存正比于所有版本的总长度，只用于小规模输入。
白盒测试（`fuzz`、`stress`）里另有各自内嵌的字符串模型，同样只用 `std::string` 的基本操作。

### 3.2 白盒随机测试 `tests/fuzz.cpp`

每轮随机选择字母表大小（1–26）、初始长度（0–3000）、步数（20–400）和基版本选取方式（总是最新 /
均匀随机 / 固定一个版本 / 混合）。**每一次编辑之后**检查：

1. *冻结池审计*：编辑前就存在的全部节点与私有副本 `memcmp` 相同；
2. 新版本文本与模型相同；基版本文本仍与模型相同；
3. 新版本的结构不变量（I3–I6）：堆序、左子树大小、每个节点的哈希既与孩子重算一致，又与直接从
   字符重算一致；
4. 树深 ≤ 12·log₂(n+2)+12；新增节点数 ≤ 40·log₂(n+2)+64；
5. 版本号等于"此前版本数"。

每次查询与模型比较；`lcp()` 还与 `lcp_reference()`（朴素二分）比较；查询前后节点数不变。查询有
一半是"瞄准"的（在另一个版本里找真实出现的子串、从真实回文中心扩展），否则随机文本上 EQUAL 几乎
总是 NO。每轮结束时**回读全部版本**并重新检查不变量，最后再做一次冻结池审计（确认查询也没有
写节点）。

5000 轮的统计：104 790 个 YES 答案，32 354 个不小于 16 的 LCP 答案；单次编辑最多新增 56 个节点，
最大树深 37。

### 3.3 黑盒差分 `tests/diff.sh`

`gen` 生成输入，分别交给 `tte`（真实程序，含输入解析）和 `naive`，比较输出字节。每个种子跑
8 种工作负载 × 8 种规模/字母表组合 = 64 个输入：

- 工作负载：`mix`（均匀随机旧版本）、`chain`（总是最新）、`branch`（版本 0、i/2、随机、最新混合）、
  `revmove`（REVERSE/MOVE 为主）、`lcp`（LCP 为主）、`pal`（回文文本、PAL 为主）、
  `edge`（空区间、全区间、位置 0 与末尾）、`flip`（同一区间反复反转并与 0/1/2 步之前的版本比较）；
- 规模：(n, q) 从 (1, 30) 到 (2000, 600)，字母表 1、2、3、4、26。

答案分布（n = 300, q = 400 的抽样）：各模式 YES 占 40–70%，LCP 答案中 30–60% 非零，最大值接近
全长——不是"全是 NO、全是 0"的无效测试。

### 3.4 满规模测试 `tests/stress.cpp`

|S₀| = 200000、每个场景 20 万次操作。朴素模型无法保存 20 万个 20 万字符的版本，所以模型只保留
"活跃版本"的文本：最新的 5 个，加上至多 6 个被钉住的旧版本（版本 0 永远钉住，最早钉住的两个不再
释放）。编辑只基于活跃版本，查询只比较活跃版本，所以每个答案都被精确校验。

| 场景 | 编辑 | 查询（YES / 平均 LCP） | 最大长度 | 节点内存 | 最大树深 |
|---|---|---|---|---|---|
| 随机 26 字母 | 109 707 | 90 293（9 164 / 7 437） | 200 084 | 141 MiB | 46 |
| 全 a 加少量 b | 110 214 | 89 786（37 418 / 10 270） | 200 085 | 138 MiB | 46 |
| 周期 3（abcabc…） | 110 049 | 89 951（11 347 / 7 714） | 200 087 | 137 MiB | 47 |
| 随机二元、插入多 | 110 048 | 89 952（10 871 / 7 190） | 200 364 | 134 MiB | 44 |
| 先插入到 40 万 | 114 202 | 85 798（8 723 / 7 973） | 400 000 | 145 MiB | 47 |

每个场景约一半的查询落在"至少 5 个版本之前"的旧版本上；被钉住的最老版本（例如第 976、233 号）
在其后 10 万多个版本产生之后仍被逐字符回读并重新验证全部不变量。

### 3.5 消毒器 `make sanitize`

以 `-fsanitize=address,undefined -D_GLIBCXX_ASSERTIONS -DTTE_POOL_STRESS` 重新编译单元测试、
白盒测试和主程序。`TTE_POOL_STRESS` 让节点池每次扩容都 `malloc` 新块并释放旧块（小池时每次分配都
搬家），于是任何"跨越分配仍持有节点引用/指针"的代码都会被 ASan 报告为释放后使用。结果：无报告。

### 3.6 双基构建 `make dual` 与碰撞演示 `make collide`

`make dual`：`-DTTE_HASH_BASES=2`，节点 48 字节，重跑单元测试、白盒 300 轮、黑盒 192 个输入，
全部通过；`bench/run.sh` 还比较了单基与双基程序在 7 个满规模输入上的输出，逐字节相同。

`make collide`：`-DTTE_MERSENNE_EXPONENT=13`，哈希模数变为 8191。此时碰撞频繁发生。白盒测试在
这种构建下仍要求文本、不变量、冻结池审计**完全精确**，而对查询答案只容忍设计允许的那一种错误
（EQUAL/PAL 把"不同"说成"相同"、LCP 偏大），并统计次数：

```
fuzz: hash modulus 2^13 - 1: 17 answers were wrong because of collisions,
      every one of them in the permitted direction
```

85 395 次查询中 17 次出错，即 2.0×10⁻⁴，与"每次不等比较约 1/p = 1.2×10⁻⁴"的量级吻合。没有出现
任何反方向的错误（把相同说成不同、LCP 偏小）。这个测试的意义是把"概率正确"变成看得见的东西：
它证实了错误的单边性，也说明了为什么实际模数要取 2⁶¹−1。

## 4. 专门针对"持久化 + 反转 + 区间操作"组合的测试

题目特别指出这一组合容易让旧版本被意外修改。针对它的检查有四层：

1. **物理层**：冻结池审计。不看语义，直接断言旧节点的字节不变。任何"为了下推标记/改孩子而写旧
   节点"的实现都过不了这一关。
2. **语义层**：每次编辑后回读基版本，每轮结束回读全部版本，`stress` 回读 10 万个版本之前钉住的
   版本。
3. **专项单元测试**：重叠区间的反转在三个不同基版本上交替进行，每一步回读所有版本；同一区间反转
   200 次；反转内部再反转、再整体反转回来。
4. **变异测试中的专项变异体**（第 5 节）："直接交换共享节点的孩子来实现反转"、"`with` 改写冻结
   节点"、"育婴区边界差一"、"就地改写时忽略方向位"、"翻转的节点不交换孩子 / 不翻转孩子 / 不交换
   哈希"——全部被杀死。

## 5. 变异测试：测试本身够不够强

`tests/mutation.py` 向源码副本中植入一个小而合理的错误（一处文本替换，必须恰好匹配一次），重新
编译并运行单元测试、白盒测试、黑盒差分；测试失败、崩溃或超时都算"杀死"。只浪费时间或内存而不
改变任何答案的变异体没有列入（例如去掉 `split` 的提前返回）。

结果：**44 个变异体全部被杀死。**

| 类别 | 数量 | 例子 |
|---|---|---|
| 方向位 / 反转 | 6 | 翻转节点不翻转孩子；`forward` 不交换哈希；`reverse` 忘记 `flip`；长度 2 的区间不反转 |
| 持久化 / 写共享节点 | 6 | `with` 改写冻结节点；交换共享节点的孩子；育婴区边界差一；`seal` 漏掉右子树 |
| 下标算术 | 10 | `split` 的 `<=` 写成 `<`；MOVE 的 p 按原串坐标解释；DELETE 保留了错误的后缀 |
| 平衡 | 2 | `merge` 比较方向相反；`build` 建成小根堆 |
| 哈希 | 5 | `mul_mod` 折叠位错；`sub_mod` 不借 p；节点公式用错幂次；`head` 幂次差一 |
| 查询 | 15 | EQUAL 忽略长度；`same_text` 缩放用反；PAL 镜像错端；LCP 上限差一、不测试就相信上限、下降测错位置、`seek` 退栈不足 |

分工情况：单元测试杀死 44 个，白盒测试杀死 44 个，黑盒差分杀死 42 个。黑盒差分漏掉的两个是
"平衡"类——答案仍然正确，只是树退化、堆序被破坏，只有检查不变量的白盒测试看得见。

第一次运行变异测试时，有两个变异体（"长度 2 的区间不反转"、"同引用捷径忽略偏移"）只被白盒和
黑盒随机测试杀死，单元测试没有发现；据此补了两组单元测试断言（见 7.6）。

## 6. 性能与内存

**关于计时的可信度。** 测试机是共享虚拟机，同一个二进制在不同时段的耗时相差可达 1.5 倍（7.4 节）。
下面的时间应理解为量级；节点数、内存、指令数是确定的。

### 6.1 整个程序（`bench/run.sh`）

|S₀| = 200000，q = 200000，从读入到写出；时间与峰值常驻内存由 `wait4` 取得。

| 输入 | 单基：时间 / 峰值内存 | 双基：时间 / 峰值内存 |
|---|---|---|
| 混合操作，随机旧版本 | 0.77 s / 121 MiB | 0.90 s / 177 MiB |
| 重度分叉，3 个字母 | 0.98 s / 123 MiB | 0.90 s / 180 MiB |
| REVERSE/MOVE 交错，2 个字母 | 0.77 s / 173 MiB | 1.27 s / 255 MiB |
| LCP 为主，单一字母（答案极长） | 1.26 s / 66 MiB | 1.75 s / 95 MiB |
| LCP 为主，26 个字母 | 0.61 s / 66 MiB | 0.89 s / 95 MiB |
| 20 万次 MOVE（三个切点均匀随机） | 1.53 s / 393 MiB | 2.40 s / 583 MiB |
| **内存最坏**：先插入到 40 万，再 19 万次 MOVE | 1.73 s / **414 MiB** | 2.57 s / **614 MiB** |

两种构建在全部 7 个输入上的输出逐字节相同。限制是 768 MB：单基最坏情形用掉 54%，双基 80%。

"内存最坏"的依据：新增节点最多的编辑是三个切点互相远离的 MOVE（每次约 64 个节点，2 KB），文本越长
路径越长；题目允许的最长文本是 40 万（20 万 + 全部插入额度）。按"三条路径完全不重合"的上界
3·(2 ln n + 2) ≈ 83 个节点估算，单基也不超过 520 MiB。

### 6.2 各操作（`build/bench`，|S₀| = 200000）

| 编辑（各 20 万次） | 每次耗时 | 每次新增节点 | 每次新增内存 |
|---|---|---|---|
| 建立初始版本（一次） | 24 ms | 200 000 | 6.1 MiB |
| INSERT 20 个字符 | 8.0 µs | 44.4 | 1.4 KB |
| DELETE ≤ 20 个字符，随机旧版本 | 3.9 µs | 22.9 | 0.7 KB |
| REVERSE，最新版本 / 随机旧版本 | 5.8 / 7.9 µs | 42.1 / 43.3 | 1.3 KB |
| MOVE，最新版本 / 随机旧版本 | 8.8 / 11.7 µs | 60.7 / 62.2 | 1.9 KB |
| 最坏：1 万次 INSERT + 19 万次 MOVE | 10.5 µs | 63.8 | 2.0 KB（合计 395.7 MiB） |

新增节点数与理论吻合：INSERT 20 字符是 44.4 ≈ 2 ln n + 20（2 ln 200000 = 24.4）；
DELETE / REVERSE / MOVE 约为 1 / 2 / 3 条路径。各场景结束时树深 42–49（n = 2×10⁵ 到 4×10⁵）。

| 查询（各 20 万次，2000 个版本上随机） | 随机 26 字母 | 单一字母 | 周期 2 |
|---|---|---|---|
| EQUAL，等长随机区间 | 4.0 µs | 1.8 µs | 3.5 µs |
| PAL，随机区间 | 1.8 µs | 1.5 µs | 2.7 µs |
| LCP，随机位置 | 2.3 µs（平均答案 0.1） | 9.2 µs（53 399） | 8.7 µs（5 740） |
| LCP，两个版本的同一位置 | 2.3 µs（454） | 11.3 µs（74 664） | 7.5 µs（6 399） |

LCP 是最贵的查询：答案很长时要在第二棵树上反复重新定位（DESIGN.md §9），而每访问一个节点基本
就是一次缓存未命中。答案短时（随机文本）它只比一次定位稍贵。

**与版本数量的关系。** "REVERSE，最新版本"在一条 20 万版本的链上进行，"随机旧版本"在 20 万个
版本构成的宽树上进行，两者每次新增节点数相同（42 对 43），耗时相差约 1.3 倍——差别来自缓存：
随机旧版本的路径节点散布在几百 MB 的池里。渐近复杂度与版本数无关，常数受缓存影响。

### 6.3 确定性的度量：指令数

用 callgrind 统计（n = 200000，2 万次操作，扣除读入与建树的 6100 万条指令）：

| 工作负载 | 每次操作的指令数 |
|---|---|
| MOVE（三个切点均匀随机） | 约 23 500 |
| 混合操作（`mix`，26 字母） | 约 8 200 |
| LCP 为主（单一字母，答案极长） | 约 11 100 |
| LCP 为主（26 字母） | 约 6 300 |

## 7. 发现的问题、原因与修复

按发现顺序。正确性方面，三层随机测试在第一次运行时就全部通过，此后的每次重构也没有出现过答案
错误；下面列出的是性能缺陷、设计调整和**测试自身**的错误。

### 7.1 幂表每次插入都整表重分配（性能缺陷）

- **现象**：第一次基准测试中 INSERT 每次 178 µs，是其他编辑的 40 倍。
- **原因**：`Powers::ensure` 里写了 `pw_.reserve(max_exponent + 1)`。`reserve` 按精确大小分配，
  文本每变长一点就把整张 20 万项的表复制一遍，每次插入 O(n)。
- **修复**：删去 `reserve`，由 `push_back` 几何增长。
- **复测**：INSERT 降到 2.8 µs（当时的测量）；答案校验和不变。

### 7.2 查询为了读"子树大小"而加载路径外的节点（设计调整）

- **现象**：随机位置的 LCP 答案几乎为 0，却要 3.1 µs；EQUAL 2.8 µs。
- **原因**：节点存的是整棵子树的大小，判断往左还是往右要读左孩子的大小，往右走还要读左孩子的
  哈希——每一步都多加载一个不在路径上的节点，多一次缓存未命中。
- **修复**：节点改存左子树大小，整棵的大小自顶向下携带；往右走时用
  f(左·根) = f(整棵) − x^(|左|+1)·f(右) 代替读左孩子。EQUAL / PAL / LCP 统一建立在"只走路径的
  前缀哈希"上，PAL 改写为与镜像做 EQUAL。
- **复测**：EQUAL 2.76 → 1.87 µs，随机位置 LCP 3.12 → 2.13 µs（同一时段测量）；全部测试通过，
  基准的答案校验和与修改前逐项相同。

### 7.3 一次编辑创建的临时节点是所需的三倍（内存与性能）

- **现象**：最初的实现是纯函数式的 `split`/`merge` 加一个"提交时把幸存节点搬到一起"的步骤。
  callgrind 显示每次 MOVE 约 22 000 条指令，其中约 40% 花在创建随后就被丢弃的节点和搬迁上：
  每次 MOVE 创建约 195 个节点，只有约 61 个留下。
- **修复**：操作自己创建的节点就地改写（`with`）；DELETE 改用单侧的 `take`（原来的写法会把被删
  区间两侧的路径节点留成垃圾）。这样没有垃圾产生，搬迁步骤整个删去，`commit` 里加了恒开的记账
  断言。
- **复测**：每次编辑的新增节点数与修改前**完全相同**（42.1 / 60.7 / 22.9 / 44.4，说明两种实现
  产生同样的新版本），总指令数减少约 20%；全部测试通过，校验和不变。针对新引入的"新生/冻结"
  区分，变异测试里有 6 个专项变异体，全部被杀死。

### 7.4 墙钟时间不可跨时段比较（测量方法）

- **现象**：7.3 的修改指令数更少，测出来却慢了近一倍。
- **原因**：同一个旧二进制重跑也慢了约 40%——是机器变慢了，不是代码。
- **处理**：此后的优化决策只依据 callgrind 指令数和**交错运行**的 A/B 对比（交错对比中新版本快
  约 10%）。曾试验给节点池申请透明大页，交错对比没有稳定收益，已删除。

### 7.5 消毒器配置下的节点池是平方复杂度（测试配置）

- **现象**：第一次 `make sanitize` 两分钟没跑完。
- **原因**：`TTE_POOL_STRESS` 最初每分配一个节点就把整个池复制一遍，10 万节点的单元测试需要
  10¹⁰ 次复制。
- **修复**：改为小池时逐个增长、之后每次增长 1/64，仍然每次都搬家。32 秒跑完，无报告。

### 7.6 测试自身的错误与缺口

- **单元测试的期望值写错（2 处）**，运行前手工复核时发现：`a²⁵⁰⁰ b a²⁵⁰⁰` 明明是回文，断言写成了
  "不是"；"答案与种子无关"一项里的一个 EQUAL 区间越界。已改正。
- **满规模测试的"增长到 40 万"场景没有生效**：场景传入的插入比例是 0，增长阶段的插入于是落入
  删除分支。测试照样"通过"，是它自己打印的 `max length 200000` 暴露了问题。修正后该行为
  `max length 400000`。教训：测试要报告它实际覆盖了什么，而不只是"通过"。
- **"插入多"场景在插入额度用完后变成了"删除多"**（同一处分支结构）。已改为额度用完后改做反转。
- **变异测试暴露的单元测试缺口**：见第 5 节末尾。补充了"长度恰为 2 的反转"和"同一版本不同位置
  的 EQUAL / LCP"的断言；复跑后单元测试杀死全部 44 个变异体。
- **变异体耗尽内存**：个别变异体陷入"边循环边分配"，第一次运行时触发了系统的 OOM 终止。给被测
  进程加了 2 GiB 的地址空间上限，并缩短了超时。
- **Clang 警告**：GCC 下无警告的代码在 Clang 的 `-Wconversion` 下有符号转换警告（哈希分量下标、
  朴素验证器的 `long` 下标）。已全部消除；朴素验证器的回文判断顺带改成了"取子串、反转、比较"
  三行。

## 8. 没有做到或无法验证的部分

- **哈希碰撞的概率界是推导出来的，不是测出来的。** 2⁶¹−1 下的碰撞无法通过运行观察到；能做的只是
  在小模数下验证错误的方向和量级（3.6 节）。
- **期望复杂度同样是推导 + 抽样。** 测试中观察到的最大树深是 49（n = 4×10⁵），但"不会退化"是
  概率陈述。
- **计时受环境影响大**（7.4）。没有硬件性能计数器（`perf` 不可用），缓存未命中的判断来自
  "指令数不变而时间变化"的间接证据和 A/B 实验。
- **只在 Linux x86-64 上编译运行过**（GCC 13、Clang 18）。`realloc` 回退路径（非 Linux）没有
  运行过。
- **朴素验证器只能跑小规模。** 满规模测试用的是"只保留活跃版本"的模型，它覆盖不到"在 20 万个
  版本中任意分叉"的全部组合；任意分叉由小规模的黑盒/白盒测试覆盖，满规模下由钉住的旧版本抽样
  覆盖。
- **LCP 没有做到最坏 O(log n)**，答案很长时是 O(log² n)（DESIGN.md §9）。
- **变异测试的 44 个变异体是手工挑选的**，不是穷举；它说明测试对这些错误类别敏感，不能证明没有
  别的漏网类别。
