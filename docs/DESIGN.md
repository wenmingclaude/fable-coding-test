## 1. 一段话概括

每个版本是一棵二叉树的根，树的中序遍历就是该版本的文本；不同版本的树共享没有变化的子树。
节点一经"冻结"便永不修改。一棵子树由"节点编号 + 一个方向位"来指代：方向位为 1 表示"把这个
节点镜像着读"。于是**区间反转只是翻转一个引用里的一个比特**，不碰任何节点。树的平衡靠随机
优先级（treap），因此树形只取决于内容，与编辑历史无关。每个节点存着子树文本的多项式哈希和
反向文本的哈希，三种查询都由它们在 O(log n) 个节点上拼出来。

核心代码：[`src/editor.hpp`](../src/editor.hpp)（约 450 行）、[`src/hash.hpp`](../src/hash.hpp)、
[`src/pool.hpp`](../src/pool.hpp)。

## 2. 数据结构

### 2.1 节点（32 字节）

```cpp
struct Node {
    Ref  left, right;   // 两个孩子（按"正向"读时的左、右）
    u32  lsize;         // 左子树的字符数
    u32  key;           // (随机优先级 << 5) | 字符编码；整个字作为大根堆的键
    Hash f, b;          // 子树文本的哈希、子树文本反转后的哈希
};
```

一个节点代表字符串 `text(left) + 自己的字符 + text(right)`。

### 2.2 引用与方向位

```cpp
using Ref = u32;            // (节点编号 << 1) | 方向位；编号 0 是空树
struct Tree { Ref ref; u32 size; };   // 一棵子树及其长度
```

方向位为 0：照节点原样读。方向位为 1：读它的**镜像**——左右孩子互换、孩子的方向位各自再翻转、
`f` 与 `b` 互换。全部代码里只有一个函数解释方向位：

```cpp
View expose(Tree t) const {
    const Node& n = pool_[t.ref >> 1];
    const u32 rsize = t.size - 1 - n.lsize;
    return (t.ref & 1) ? View{{flip(n.right), rsize}, {flip(n.left), n.lsize}, n.key}
                       : View{{n.left, n.lsize}, {n.right, rsize}, n.key};
}
```

其余算法（分裂、合并、查询）都只和 `View` 打交道，写的时候完全不必想"这里是不是被反转过"。

节点只存左子树大小而不存整棵子树大小：整棵的大小在根处已知（版本表里有），往下走时
`左 = lsize`、`右 = size − 1 − lsize` 顺手推出。这样沿一条路径向下时**不需要为了读大小而去加载
路径外的兄弟节点**（见 6.1）。

### 2.3 版本表与节点池

- `versions_[v]`：版本 v 的根（一个 `Tree`，8 字节）。
- `pool_`：所有版本的所有节点，一个连续数组，按下标寻址。
- `mark_`：分界线。下标 `< mark_` 的节点是**冻结**的；下标 `≥ mark_` 的节点是**当前这一次编辑
  操作刚创建的**（下文叫"育婴区"）。操作结束时 `commit` 给育婴区节点算好哈希，并把 `mark_` 推到
  池尾——它们从此冻结。

## 3. 背后的代数

把字母 a..z 编码为 1..26。对字符串 s = s₀s₁…s_{n−1}，取素数 p = 2⁶¹ − 1 和一个随机的 x，定义

```
f(s) = Σ sᵢ · xⁱ        (mod p)          —— s 的哈希
b(s) = Σ sᵢ · x^(n−1−i) (mod p)          —— s 反转后的哈希，即 b(s) = f(rev s)
μ(s) = ( n, f(s), b(s) )                  —— s 的"摘要"
```

两条恒等式是全部设计的地基：

```
连接：  μ(s·t)   = ( |s|+|t|,  f(s) + x^|s|·f(t),  b(t) + x^|t|·b(s) )
反转：  μ(rev s) = ( |s|, b(s), f(s) )            ← 只是交换两个分量
```

第一条说明：一棵子树的摘要可以由左右孩子的摘要 O(1) 算出（节点里存的 `f, b` 就是这么来的）。
第二条说明：镜像着读一个节点时，它的摘要不用重算，交换 `f` 和 `b` 即可（`expose` 旁边的
`forward()` / `summary()` 就做这件事）。

**线性代数的看法。** 把字符串 s 对应到 2×2 矩阵

```
M(s) = | x^|s|   f(s) |
       |   0       1  |
```

直接乘一下可以验证 M(s·t) = M(s)·M(t)：**字符串连接就是矩阵乘法**。等价地，s 对应一个仿射变换
h ↦ f(s) + x^|s|·h（"在一个哈希为 h 的字符串前面接上 s"）。矩阵乘法满足结合律，所以一长串乘积
怎么加括号都行——一棵二叉树正是一种加括号的方式，每个节点存着"自己这一段的乘积"。平衡树的全部
作用，就是保证任何一段连续区间都能由 O(log n) 个已经算好的乘积拼出来。

反转不是同态而是"反同态"：rev(s·t) = rev(t)·rev(s)，顺序倒过来。单凭 M(s) 算不出 M(rev s)，
所以每个节点把 M(s) 和 M(rev s) 都存下来；反转操作就是交换这两者。

`tests/unit.cpp` 的 "summary is a homomorphism" 一项直接按定义逐字符计算 μ，检验上面两条恒等式、
结合律、单位元、rev(st) = rev(t)rev(s)，以及"回文 ⟺ f = b"。

## 4. 不变量

记 S_v 为版本 v 应有的文本。任何两次操作之间，下面各条同时成立：

| 编号 | 不变量 | 由谁检查 |
|---|---|---|
| **I1 文本** | `versions_[v]` 的中序遍历（按方向位解释）恰为 S_v | 每次编辑后与模型逐字符比对 |
| **I2 冻结** | 下标 `< mark_` 的节点的任何字节都不再改变 | `fuzz` 的"冻结池审计"：每次编辑后对全部旧节点做 `memcmp` |
| **I3 封闭** | 冻结节点的孩子都是冻结节点；版本根都是冻结节点。因而任一版本可达的节点全在冻结区 | `check_invariants` |
| **I4 堆序** | 任一节点的 `key` ≥ 其孩子的 `key` | `check_invariants` |
| **I5 大小** | `lsize` 等于左子树的字符数 | `check_invariants` |
| **I6 摘要** | `f`, `b` 分别等于子树文本及其反转的哈希 | `check_invariants`：既由孩子重算，又直接由字符重算 |
| **I7 育婴区** | 操作进行中：育婴区节点只从本次操作的局部变量可达，且每个恰被引用一次；操作结束时全部属于新版本 | `commit` 里的记账断言（始终开启） |
| **I8 规范形** | 一棵树的形状只由"字符序列 + 各字符的优先级"决定（优先级相同的情形除外），与它是经过怎样的编辑得到的无关 | 由 I4 推出，见 8.1 |

## 5. 编辑操作

### 5.1 三个基本动作

**分裂** `split(t, k)`：把 t 分成"前 k 个字符"和"其余"两棵树。

```cpp
std::pair<Tree, Tree> split(Tree t, u32 k) {
    if (k == 0) return {Tree{}, t};
    if (k == t.size) return {t, Tree{}};
    const View v = expose(t);
    if (k <= v.left.size) {
        auto [a, b] = split(v.left, k);
        return {a, with(t, b, v.right)};        // 根留在右半边，左孩子换成 b
    }
    auto [a, b] = split(v.right, k - v.left.size - 1);
    return {with(t, v.left, a), b};             // 根留在左半边，右孩子换成 a
}
```

只有"切口落在其子树内部"的节点才需要一份新副本——也就是从根到切口的那一条路径。两条提前返回
（k = 0 或 k = size）保证切口恰在子树边界时不产生任何副本。

**合并** `merge(a, b)`：得到文本为 text(a)+text(b) 的树。优先级大的那个根做新根，另一棵递归地
并入它的内侧孩子。只有 a 的右脊和 b 的左脊上的节点需要新副本。

**截取** `take(t, k)`：只要前 k 个字符，丢掉的那部分一个节点也不创建。后缀不需要另写一个函数：
**后缀就是"镜像的前缀"的镜像**，`flip(take(flip(t), n − r))`。

`with(t, left, right)` 的含义是"t 的根，换上新的孩子"。若 t 的根是冻结节点，就**新建**一个节点
（冻结节点绝不写入）；若是本次操作自己刚创建的育婴区节点，就**就地改写**它（它只被本操作引用
一次，没有别人看得见）。这使得一次编辑实际分配的节点数恰好等于新版本真正需要的新节点数。

### 5.2 四种编辑

```
INSERT v p s :  (a, b) = split(t, p)                       → merge(merge(a, build(s)), b)
DELETE v l r :                                             → merge(take(t, l), flip(take(flip(t), n−r)))
REVERSE v l r:  (a, rest) = split(t, l); (mid, b) = split(rest, r−l)
                                                           → merge(merge(a, flip(mid)), b)
MOVE v l r p :  (a, rest) = split(t, l); (mid, b) = split(rest, r−l)
                (x, y) = split(merge(a, b), p)             → merge(merge(x, mid), y)
```

`build(s)` 用单调栈在 O(|s|) 内建出一棵新 treap（键序列的笛卡尔树）；初始串 S₀ 也是这样建的。

不改变文本的编辑（空区间的 DELETE/MOVE、长度 < 2 的 REVERSE、原地 MOVE）直接让新版本指向原来的
根，分配 0 个节点。

### 5.3 提交

`commit(top)` 自顶向下只走育婴区节点（冻结节点不会指向育婴区，走到冻结节点即可停），自底向上
为每个育婴区节点计算 `f, b`，然后把 `mark_` 推到池尾。它同时数一下自己封存了多少节点，必须恰好
等于本次操作分配的节点数，否则抛出异常：少了说明有节点被遗弃（内存泄漏），多了说明有节点被引用
了两次（违反 I7）。

哈希**推迟到提交时才算**，是因为一次 MOVE 中同一个育婴区节点会被改写 3 次左右，只有最终形态
需要哈希。

## 6. 查询操作

三种查询都不创建节点、不写任何节点。

### 6.1 前缀哈希：`walk`

`prefix_hash(t, k)` 返回 t 的前 k 个字符的哈希 f(t[0,k))。从根向位置 k 走：往左走时什么也不用加；
往右走时要把"左子树 + 根字符"这一段加进来。这一段的哈希不去读左子树，而是用减法得到：

```
f(左·根字符) = f(整棵子树) − x^(|左|+1) · f(右子树)
```

右子树正是下一步要去的节点。于是一次前缀查询**只加载路径上的节点**，路径外的兄弟一个都不碰
（对缓存很重要：路径外的节点多半不在缓存里）。

### 6.2 EQUAL

区间哈希由两个前缀哈希相减得到：f(a[0,r)) − f(a[0,l)) = x^l · f(a[l,r))。比较两个区间时不做
除法，而是两边各乘对方的 x 的幂，统一到公因子 x^(l₁+l₂)：

```
(P_a(r₁) − P_a(l₁)) · x^l₂  ==  (P_b(r₂) − P_b(l₂)) · x^l₁
```

因为 x ≠ 0，这与 f(a[l₁,r₁)) = f(b[l₂,r₂)) 等价。长度不同直接回答 NO。

### 6.3 PAL

回文就是"等于自己的镜像"的文本，而一棵树的镜像就是用翻转的引用去读同一棵树：

```cpp
return same_text(t, l, r, flip(t), t.size - r);
```

也就是说 `PAL v l r` 被归结为 `EQUAL`：v 的 [l, r) 与"v 的镜像"的 [n−r, n−l) 比较。没有任何
专门为回文写的代码；节点里的 `b` 正是为了让镜像读法也有现成的哈希可用。

### 6.4 LCP

设两段后缀为 A[p₁..]、B[p₂..]。定义谓词 ok(L)："A[p₁, p₁+L) 与 B[p₂, p₂+L) 哈希相同"。它对 L
单调（真…真假…假），答案是最大的使 ok 为真的 L。朴素做法是对 L 二分，每次求两个区间哈希，共
O(log² n)。这里做了两点改进。

**(1) 让 A 这一侧的每次探测只花 O(1)。** 走到 p₁ 的路径把 p₁ 周围的子树从小到大列了出来
（代码里的"指针栈" `A`）。探测点不取任意的 L，而取 A 自己的结构给出的"自然断点"：

- *上爬*：依次测试包含 p₁ 的、越来越大的子树的右端点。每个端点处 A 的前缀哈希由栈里现成的量
  O(1) 得到。直到某个端点失配（或越过了长度上限）。
- *下降*：答案就在那棵子树里。从它的根开始，每到一个节点测试"匹配能否越过这个节点的字符"：
  能就往右走，不能就往左走。同样每步 O(1)。

这其实就是平衡树上的"指针搜索"（finger search）：先向上走到恰好包住答案的子树，再向下走。

**(2) 让 B 这一侧的每次探测只花"两次探测点之间的树上距离"。** B 侧需要在 A 指定的位置求前缀
哈希。`seek` 维护另一个指针栈：新位置若不在栈顶子树里，就退栈到包含它的祖先，再向下走。相邻
两次探测点相距 d 时，这一步的期望代价是 O(log d)，而不是每次都从根出发的 O(log n)。

**上限也是一个断点。** 上爬时若下一棵子树已经越过长度上限 `end`，先直接测试 `end` 本身：两段
文本一直相同到末尾，这是很常见的情形（比较一个版本与它的派生版本时尤其如此），也正好是下降阶段
最贵的情形。

**单边性。** 相等的字符串哈希必然相等，所以所有 L ≤ 真实 LCP 的探测一定为真；算法返回的值只会
≥ 真实值，仅在发生哈希碰撞时才会偏大。

`lcp_reference()` 是朴素的"二分 + 区间哈希"实现，只用于在测试中与 `lcp()` 交叉验证。

## 7. 正确性论证

### 7.1 旧版本为什么不会被修改

整个 `editor.hpp` 里**向节点写入**的地方只有四处：`make`（追加新节点）、`with` 的就地改写分支、
`build`（给刚追加的节点接上孩子）、`seal`（填哈希）。逐一检查：

- `make` 只在池尾追加；
- `with` 改写前检查 `in_nursery`，即下标 ≥ `mark_`；
- `build` 只写它自己刚 `make` 出来的节点；
- `seal` 只在 `in_nursery` 为真时才被调用。

所以下标 < `mark_` 的节点没有任何代码路径会写它（I2）。又因为冻结节点的孩子在它冻结时都已冻结
（提交时整棵新树一并冻结），冻结节点只指向冻结节点（I3）。于是：**任一已发布版本能到达的节点全部
在冻结区，而冻结区是只读的**——旧版本的文本、大小、哈希在物理上不可能改变。

这不是只靠论证：`fuzz` 在每一次编辑之后，把编辑前就存在的全部节点与一份私有副本做 `memcmp`，
任何一个字节的变化都会立刻报错（"冻结池审计"）。

### 7.2 为什么区间反转不破坏版本隔离

传统做法是在节点里放一个"待反转"的惰性标记，访问时把标记下推给孩子。在持久化的树里这有两个
著名的坑：下推要修改孩子，而孩子可能被旧版本共享；即使只是**读**一棵树也会触发下推，于是查询
也在写。必须在每次下推时复制孩子才能避免，漏掉一处，旧版本就被悄悄改掉了。

这里根本没有这类状态。"反转"这一信息不在节点里，而在**指向节点的引用**里：

- `flip(mid)` 只是把一个局部变量里的整数异或 1；
- 这个引用随后被写进一个**新建的**（或育婴区的）父节点，或者写进版本表的新条目；
- 节点自身的字节没有变；别的版本手里指向同一节点的引用也没有变，它们照旧按原方向读到原来的内容。

一个冻结节点"正着读是什么、镜像着读是什么"，都是它的字节的纯函数，永远不变。没有标记需要下推，
所以读不会引起写，反转与共享之间不存在任何交互。

### 7.3 为什么剪切移动不会产生错误的索引

题目定义：先剪掉 [l, r)，p 是**剩余字符串**里的下标。代码逐字照做：

```cpp
auto [a, rest] = split(t, l);
auto [mid, b]  = split(rest, r - l);
auto [x, y]    = split(merge(a, b), p);     // merge(a, b) 就是"剩余字符串"这棵树
return publish(merge(merge(x, mid), y));
```

`p` 直接作为 `merge(a, b)` 这棵树里的下标使用。代码里**不存在**"把 p 换算回原串坐标"的算术，
也就不存在 p 与 l、r 大小关系的分情况讨论——没有换算，就没有换算错误。
`tests/unit.cpp` 对一个 7 字符串穷举了全部 (l, r, p) 组合与定义对照。

### 7.4 为什么对历史版本的读取与查询是安全的

- 查询函数都是 `const`，只调用 `expose` / `forward` / `walk` / `seek`，它们只读节点；
- 查询不分配节点（`fuzz` 检查每次查询前后节点数不变、全部节点字节不变）；
- 版本根在版本表里按编号 O(1) 取到，取到的树完全位于冻结区（7.1）。

唯一的可变状态是 `lcp()` 复用的两个栈缓冲区，所以**同一个 `Editor` 对象不支持多线程并发查询**
（见 13）。

### 7.5 每种操作的结果正确

对树高归纳即可：`split` 返回的两棵树中序遍历分别是前 k 个与其余字符；`merge` 返回的树中序遍历是
两段的连接；`take` 是 `split` 的左半；`flip` 把中序遍历反过来（`expose` 交换孩子并递归翻转）。
把它们代入 5.2 的四个表达式，得到的正是各操作定义的字符串。I4（堆序）在 `split`（子集保持堆序）
和 `merge`（取较大的根）下保持，在 `flip` 下显然保持。

## 8. 随机化：两处，性质完全不同

| | 树的优先级 | 哈希的求值点 x |
|---|---|---|
| 影响什么 | **只影响时间和内存**（树的深度） | **只影响查询答案是否正确** |
| 类型 | Las Vegas：答案永远对，快慢是随机的 | Monte Carlo：永远一样快，答案以极小概率出错 |
| 出错方向 | 无 | 单边：只会把"不同"说成"相同" |

两者都来自同一个种子（默认取自操作系统熵源，`--seed` 可固定）。

### 8.1 优先级：期望复杂度与最坏情况

每个字符在创建时得到一个 27 位随机优先级，之后永不改变。由 I4，一棵树的根必是其中优先级最大的
字符，左右子树同理——所以树形由"当前字符序列及其优先级"唯一决定（I8）。编辑只是改变了序列，
没有改变各字符的优先级；对于一个事先不知道优先级的出题人（下称"不知情的对手"），任何版本里的
优先级都是独立同分布的随机数。因此：

> **每一个版本的树，不论它是经过多少次、怎样的编辑和分叉得到的，都服从"随机 treap"的分布。**

由此得到（n 为该版本长度）：

- 一个位置的期望深度约 2 ln n ≈ 1.39 log₂ n；
- 深度超过 c·ln n 的概率随 c 指数下降（Chernoff 界）。例如 n = 4×10⁵ 时某个节点深度 ≥ 200 的
  概率 < e⁻²⁰⁰；
- **最坏情况**：树退化成链，单次操作 O(n)，并且递归深度达到 n。这只在优先级恰好（近似）有序时
  发生，概率可忽略，但它**不是零**；所以本文所有时间界都是"期望"或"高概率"意义上的，不是确定性
  最坏界。

两点说明：

1. 这是**每次操作各自的期望界，不是均摊界**。均摊界（例如伸展树）在持久化下会失效：对手可以
   反复从同一个"昂贵"的历史状态分叉。这里每个版本都独立地满足期望界，分叉无法利用。
2. 优先级只有 27 位，偶尔会相同（n = 4×10⁵ 时任意一对相同的概率是 2⁻²⁷）。相同时代码取一致的
   规则，正确性不受影响，对平衡的影响可忽略。
3. 如果对手**知道种子**（例如固定了 `--seed` 又公开了它），就可以构造让树退化的输入。固定种子
   只应用于复现和测试。

### 8.2 哈希：碰撞风险、误判概率、防护

**误判只可能有一种方向。** 相同的字符串哈希一定相同，因此：

- `EQUAL` / `PAL` 回答 NO 时**一定正确**；回答 YES 时以极小概率错误；
- `LCP` 的返回值**不会小于**真实值；以极小概率偏大。

**单次比较的概率界。** 设 x 在 {2, …, p−2} 上均匀随机（共 p−3 个值），u ≠ v 是两个长度为 m 的
字符串。f(u) − f(v) = Σ (uᵢ − vᵢ)·xⁱ 是 x 的一个**非零**多项式，次数 ≤ m−1，在域 F_p 中至多有
m−1 个根。所以

```
Pr[ f(u) = f(v) ] ≤ (m − 1) / (p − 3)
```

本题 m ≤ 4×10⁵，p = 2⁶¹ − 1 ≈ 2.3×10¹⁸，单次比较的误判概率 ≤ 1.74×10⁻¹³。代码里的比较都形如
"x^α·f(u) 与 x^β·f(v) 统一到同一个幂次后比较"，x ≠ 0，与 f(u) = f(v) 等价，所以同一个界适用；
`PAL` 是 v = rev(u) 的特例。

**整次运行的概率界。** 查询之间有依赖（`LCP` 下一步测哪里取决于上一步的结果），不能直接把
"每次比较"当成事先固定的事件。标准做法：考虑一个"理想执行"，其中每次比较都按真实的字符串相等性
回答。理想执行里出现哪些比较与 x 无关；而真实执行与理想执行完全一致，除非理想执行中的某一次
比较发生了碰撞。对理想执行中的全部比较用联合界：

```
Pr[ 整次运行有任何一个答案出错 ] ≤ (比较次数的期望) × (m−1)/(p−3)
```

`EQUAL`、`PAL` 各 1 次比较；`LCP` 的比较次数不超过上爬与下降的步数，期望 O(log n)，宽松地按 60
计。20 万次查询全是 `LCP` 时，上界约为 1.2×10⁷ × 1.74×10⁻¹³ ≈ **2×10⁻⁶**。这是对"对手精心挑选
字符串"的最坏情形的界；对并非针对 x 构造的输入，单次比较的实际碰撞率在 1/p ≈ 4×10⁻¹⁹ 量级。

这个数字**不是零**。本实现的查询答案是"以至少 1 − 2×10⁻⁶ 的概率全部正确"，而不是"正确"。

**防护措施。**

1. *求值点保密且每次运行重新随机。* 上面的界要求 x 的选取独立于输入。x 取自操作系统熵源，
   不出现在任何输出里。**固定并公开种子会使这个界失效**：知道 x 的人可以构造碰撞。
2. *模数是素数 2⁶¹ − 1，而不是 2⁶⁴ 自然溢出。* 模 2⁶⁴ 的多项式哈希存在不依赖于基的通用碰撞
   构造（Thue–Morse 串），随机化 x 也无济于事；素域上没有这个问题。
3. *错误是单边的*，调用方可以据此决定是否在回答 YES 时追加逐字符验证（代价是 O(长度)）。
4. *可选的双基模式。* 以 `-DTTE_HASH_BASES=2` 编译（`make dual`）时，哈希取两个独立随机点上的值，
   节点从 32 字节变为 48 字节。两次求值独立，单次比较的界变为平方：≤ 3×10⁻²⁶，整次运行
   ≤ 4×10⁻¹⁹。代价是内存 +50%、时间略增（实测见 TESTING.md）。在 768 MB 限制下两种模式都放得下。
5. *看得见的失败。* `make collide` 把模数换成很小的梅森素数 2¹³ − 1，此时碰撞大量发生；测试验证
   所有错误答案都落在允许的方向上（见 TESTING.md）。

**为什么不追求零错误？** 存在确定性的方案（把字符串分层"签名"、使相等的子串得到相同的标识，
见 12），但常数和代码复杂度都大得多。在明确说明了概率界、且可以用双基模式把它压到 10⁻¹⁹ 的
前提下，这里选择了哈希。

## 9. 复杂度

n 为被操作版本的长度，m 为插入串长度，ℓ 为 LCP 的答案。"期望"是对优先级取的（8.1）。

| 操作 | 时间（期望） | 新增节点（期望） | 最坏情况 |
|---|---|---|---|
| 建立 S₀ | O(n) | n | O(n)（确定性） |
| INSERT | O(log n + m) | ≈ 2 ln n + m | O(n + m) |
| DELETE | O(log n) | ≲ 2·2 ln n | O(n) |
| REVERSE | O(log n) | ≲ 2·2 ln n | O(n) |
| MOVE | O(log n) | ≲ 3·2 ln n | O(n) |
| EQUAL / PAL | O(log n) | 0 | O(n) |
| LCP | O(log n + log²(ℓ+2)) | 0 | O(n) 级 |
| 取版本根 | O(1) | 0 | O(1) |

"最坏情况"一列对应树退化（概率可忽略，见 8.1）。新增节点数的常数来自"每个切口/接缝处约有一条
根到叶的路径需要新副本"：DELETE 两个切口挨得近时接近 1 条路径，REVERSE 2 条，MOVE 3 条。实测
（n = 2×10⁵）分别约为 23、43、61 个节点，即每次编辑 0.7–2 KB。

**LCP 的界。** 初始两次定位 O(log n)。上爬阶段的探测点是从 p₁ 向右、优先级依次创新高的那些
位置，在距离 ℓ 以内期望有 O(log ℓ) 个；越过 ℓ 的第一个探测点的距离 D 满足 Pr[D > s] = ℓ/s，
故 E[log²(D/ℓ)] = O(1)。下降阶段在一棵大小约 D 的子树里走 O(log D) 层。每次探测在 B 侧的代价是
O(log(相邻探测点间距))。合计期望 O(log n + log²(ℓ+2))：随机文本上 ℓ 很小，LCP 只比一次定位
稍贵；ℓ 很大时退到 O(log² n)。未能做到对所有情形都是 O(log n)：两棵形状无关的树没有共同的
"自然断点"，一侧 O(1) 的探测点对另一侧总要付出 O(log) 的定位代价。

### 9.1 为什么复杂度不随历史版本数量增长

1. **找到一个版本是 O(1)**：版本表是数组。
2. **一次操作只在一两棵树上走几条根到叶的路径**，路径长度只取决于那棵树自己的长度。由 I8，
   每个版本的树形与"它前面有多少个版本、历史怎样分叉"无关——第 20 万个版本的树和直接由同样的
   文本新建的树服从同一分布。
3. **没有任何随版本数增长的辅助结构被遍历**：没有版本间的链表、没有需要重放的修改日志、没有
   全局重建。
4. **界是逐操作的期望界而非均摊界**，所以反复从同一个旧版本分叉不会"透支"（8.1）。

实际机器上有一个与渐近无关的效应需要如实说明：节点池越大，随机访问的缓存/TLB 未命中越多，
所以后期操作的常数会比早期略大（TESTING.md 有数据）。

## 10. 内存控制

问题规模：最多 20 万次编辑，每次都要留下一个完整可查的版本，限制 768 MB。

1. **不复制文本，只复制路径。** 一次编辑新增 O(log n) 个节点（实测 23–64 个），其余全部与旧版本
   共享。
2. **节点 32 字节，没有一个字节的填充。** 两个 32 位引用、左子树大小、优先级与字符合用的一个
   32 位字、两个 61 位哈希。整棵子树的大小不存（自顶向下推出）。
3. **一次编辑分配的节点数 = 新版本真正需要的新节点数。** 朴素的函数式写法在一次 MOVE 里会创建
   约 195 个临时节点，其中只有约 61 个最终留在新版本里；不处理的话，20 万次 MOVE 需要约 1.2 GB，
   超出限制。这里让操作自己刚创建的节点就地改写（`with`），DELETE 用单侧的 `take`，于是**没有
   垃圾产生**，也就不需要垃圾回收；`commit` 的记账断言保证这一点一直成立。
4. **不改变文本的编辑不分配节点。**
5. **节点池增长时不出现两份。** `std::vector` 扩容时新旧缓冲区同时存在，400 MB 的池会瞬间需要
   900 MB。节点池在 Linux 上用 `mremap` 扩容（移动页表项而非数据），每次增长 25%。其他平台回退到
   `realloc`。

最坏情形（先插入到 40 万字符，再做 19 万次 MOVE）的实测峰值内存见 TESTING.md，约为限制的一半。

## 11. 更简洁的抽象，以及它该用到哪一步为止

题目问：能否用一个更简洁的数学抽象统一理解字符串连接、区间反转、子串哈希和版本共享？可以。

### 11.1 抽象是什么

**带对合的幺半群**（monoid with involution）：一个集合，带有满足结合律的乘法、单位元，以及一个
"取反"运算 \*，满足 (a·b)\* = b\*·a\*、(a\*)\* = a。

- 字符串是这样的结构：乘法 = 连接，单位元 = 空串，\* = 反转。
- 摘要 (长度, f, b) 也是这样的结构：乘法 = 第 3 节的连接公式，\* = 交换 f 与 b。
- **μ 是两者之间保持全部运算的映射（同态）**：μ(s·t) = μ(s)·μ(t)，μ(rev s) = μ(s)\*。
  用第 3 节的矩阵说法，这是字符串幺半群的一个线性表示。

在这个视角下，四件事成了一件事：

| 具体的东西 | 抽象里是什么 |
|---|---|
| 一棵（子）树 | 一个由"字符、连接、反转"写成的**表达式** |
| 方向位 | 表达式上的 \* 号；`expose` 是把 (a·c·b)\* 改写为 b\*·c·a\* 的那条规则，每次只往里推一层 |
| 节点里存的 f, b | 表达式的值在 μ 下的像；由同态性质自底向上算出 |
| 子串哈希 | 把子串写成 O(log n) 个现成子表达式的乘积，再对 μ 的值做同样的乘积 |
| 版本共享 | 不同的表达式共用子表达式——表达式不是树而是 DAG；"不可变"是说表达式是值，不是容器 |
| 平衡（treap） | 与上面正交：同一个字符串有很多表达式，优先级从中挑出一个又矮又唯一的 |

### 11.2 它确实让实现变简单的地方

这个抽象不是事后贴的标签，下面几处设计直接由它决定：

1. **方向位放在引用上，而不是节点里。** \* 是表达式的一部分，不是被求值对象的状态。这直接消灭了
   "惰性标记下推 × 持久化"这一整类错误（7.2），也让反转不分配内存。
2. **解释方向位的代码集中在四个小函数里**（`expose`、`forward`、`summary`、`with`），其余算法对
   方向一无所知。
3. **PAL 不需要自己的算法**：s 是回文 ⟺ s = s\*，于是 PAL 就是拿一棵树和它的 \* 做 EQUAL（一行）。
4. **后缀不需要自己的算法**：后缀 = (前缀 of t\*)\*，所以 `take` 只写了前缀版，DELETE 用它两次。
5. **测试可以直接测"定律"**：同态性、结合律、对合律各是一条性质测试，比枚举用例覆盖得多。

### 11.3 我没有照着抽象去写的地方，以及原因

1. **没有写成对任意幺半群通用的模板**（类似 finger tree 的 `Measured` 框架）。全程只有一个幺半群；
   泛化不会删掉任何一行现有代码，只会多出一层间接。更关键的是下一条。
2. **查询的快路径用到了幺半群里没有的运算：减法。** 6.1 的
   f(左·根) = f(整棵) − x^(|左|+1)·f(右) 利用了 f 取值于一个域、前缀哈希可以相减。一个只知道
   "幺半群"的通用框架做不了这件事，只能去加载兄弟节点，实测要多付约三分之一的查询时间。
   所以对查询而言，恰当的抽象其实是"带权前缀和"而不是"幺半群上的区间积"——**抽象选得过于一般，
   会把真正有用的结构藏起来。**
3. **节点里不直接存"摘要"三元组。** 长度分量由 `lsize` 自顶向下推出，直接存会让每个节点多 4 字节
   并在查询时多读一个节点。
4. **不真的存 2×2 矩阵。** 矩阵视角用来理解；存储上右下角恒为 1、左下角恒为 0，左上角 x^n 查表
   即得，只需要存 f 一个数。

### 11.4 为了性能偏离纯函数式的地方，以及代价

纯粹按 11.1 写，所有节点从创建起就不可变，`split`/`merge` 一律新建。实现里有两处偏离：

- **育婴区就地改写**（`with`）。收益：分配量降到三分之一，不需要垃圾回收，总指令数减少约两成。
  代价：多了一条不变量 I7 和一个"新生/冻结"的区分。风险控制：区分只在 `with` 一处、一行判断；
  `commit` 的记账断言始终开启；`fuzz` 的冻结池审计逐字节检查；变异测试里专门有"改写冻结节点"、
  "边界差一"、"改写时忽略方向"等变异体，全部被杀死。
- **哈希推迟到提交时计算。** 收益：每个新节点只算一次哈希。代价：操作进行中育婴区节点的哈希
  无效；因为查询只在已发布的版本上进行，这不会被观察到。

结论：这个抽象值得用来**想清楚设计和组织测试**，并且确实决定了几个关键选择；但把它原样做成
代码层面的通用框架，会增加复杂度、并丢掉对性能最重要的那个减法。所以数学用来定形，代码保持具体。

## 12. 考虑过但没有采用的方案

- **节点内惰性反转标记 + 下推**：最常见的做法。在持久化下，下推必须复制孩子，读操作也会分配
  节点，正是题目警告的那类错误的来源。方向位方案更简单，也更省内存。
- **确定性平衡树（权重平衡树 / AVL / 红黑树，基于 join）**：可以把"期望 O(log n)"换成确定性最坏
  O(log n)，随机性只剩哈希一处。代价是旋转逻辑复杂得多，且没有 treap 的规范形（历史无关性要另行
  论证）。认为不值得。
- **伸展树**：均摊界在持久化下不成立（8.1）。
- **叶子存字符块的 rope**：节点更少，但块内的反转与哈希要另行处理；当前每次编辑 0.7–2 KB，
  没有必要。
- **持久化线段树 / 可持久化数组**：下标固定时 LCP 可以两树同步下降做到 O(log n)，但不支持插入、
  删除、移动。
- **确定性字符串相等（签名 / locally consistent parsing；Mehlhorn–Sundar–Uhrig 1997，
  Alstrup–Brodal–Rauhe 2000，Gawrychowski 等 2018）**：零误判，相等的子串得到相同的标识，LCP 可以
  更快。但实现复杂度和常数都高出一个量级，且支持反转需要同时维护正反两套结构。

## 13. 已知限制

- 查询答案是概率正确的（8.2）；时间界是期望界（8.1）。
- 固定并公开种子后，对手可以针对性地构造哈希碰撞或让树退化。
- `split` / `merge` / `seal` 等是递归的，递归深度等于树深（期望约 25，实测最大 50 左右）。树退化
  时会栈溢出——与"单次操作 O(n)"是同一个概率可忽略的事件。
- 一个 `Editor` 对象不是线程安全的（`lcp()` 复用内部缓冲区）。
- 文本长度与节点总数受 32 位引用限制：节点数 < 2³¹。本题最多约 1.3×10⁷ 个节点。
- 字符集固定为 a–z（字符编码占 5 位）。
- `mremap` 路径只在 Linux 上启用；其他平台用 `realloc`，扩容时可能短暂占用两份内存。除 Linux
  (x86-64, GCC 13 / Clang 18) 外没有实际编译运行过。
